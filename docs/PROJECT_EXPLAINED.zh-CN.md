# ScholarNova 项目理解与开发学习手册

给项目开发者的一份大白话说明

核对日期：2026 年 9 月 19 日。源码基线：v1.2.5，提交 5a7cd33；出图规划校验改进另见第 15 章。本手册依据实际代码解释现状，不把路线图中的设想当作已经完成的功能。

## 1 先把项目用一句话说清楚

ScholarNova 是给个人研究者用的桌面科研工作台。它把找论文、读论文、记知识、追问材料和整理研究路线串起来，让研究者少在搜索网站、聊天窗口和笔记软件之间来回搬运内容。

可以把它理解成一位有工具的科研助理。学术数据库负责提供论文线索，解析程序把文件变成可处理的材料，模型帮助理解和表达，数据库替你保存积累。开发者的工作是把这些环节接好，并让用户知道每一步做到了什么、哪里失败、结果从哪里来。单独接通一个聊天接口，只完成了其中的一小部分。

这也是项目与 AI 应用开发真正的关系。你并没有从头训练一个千问模型，而是在解决“怎样让现成模型可靠地参与实际工作”。输入什么材料、选择哪个模型、等待多久、失败后怎么办、如何保留来源，都是应用开发的核心内容。

项目也包含数据工程，但目前不是一个已经处理海量数据的分布式大数据平台。接入多个来源、统一字段、去重、切块、建索引和保留数据来源，都是可以迁移到大数据工作的能力。用到这些方法，不等于一定要上 Hadoop 或 Spark。

阅读时不要试图一口气记住所有名词。先沿着第 3 章的例子走一遍；遇到陌生词，先看它在这一步帮你解决什么，再去读定义。能解释一个按钮背后的完整流程，比背会十种框架名称更有用。

**你读完后应当能够回答**：一条问题经过了哪些程序；模型究竟看到了哪些材料；数据保存在哪里；换模型为什么有时会失败；如何验证一次修改没有把原来的功能弄坏。

## 2 为什么值得做这件事

科研中的困难经常不是完全找不到信息，而是信息太分散。搜到几十篇论文后，还要判断是否相关、找到全文、读懂方法、摘出结论，并在下次写作时找回出处。每次重新搜索、重新解释背景、重新整理笔记，都会消耗时间。

普通聊天工具擅长解释，但用户必须自己喂材料。文献管理工具擅长管理条目和引用，却不一定负责跨材料问答。学术搜索服务擅长发现文献，也不会天然知道用户已经读过什么、当前研究要往哪个方向走。ScholarNova 适合做的，是把这些已有能力组织成一段连贯的个人工作流程。

因此，产品不应该以“调用了多少个模型”为主要成绩。一个更实际的判断是：用户提出问题后，能不能较快找到有用的论文；点开分析后，是否知道分析基于摘要还是全文；几天后回来，能不能找回自己的笔记和依据。

面向个人用户的优先级也由此确定。先把安装、配置、检索、阅读、保存和导出做好，再考虑更复杂的智能体协作。一个失败后能保留结果、讲清原因的功能，通常比多一个偶尔才能成功的按钮更有价值。

**需求和实现不是同一件事。**“让用户方便地切换千问和 GLM”是需求；模型配置、协议适配、能力检查和任务路由是实现。先说清需求，才能判断技术是不是必要。

**练习**：找一位同学，让他不用你的指导完成“找两篇论文并保存一条有出处的笔记”。记录他卡住的地方，不替他点击。这份记录比凭感觉想出的十个新功能更能指导下一轮优化。

## 3 跟着一个研究问题走完整流程

下面始终用“想研究大语言模型如何辅助交通预测”作为示例。它只是演示问题，不表示系统已经证明某个方法有效。

第一步，在设置中配置能使用的文字模型，并测试连接。这里确认的是账号、地址和模型能否完成基本请求，不代表所有任务都已经测过。分析图片、生成图片和向量检索还要分别验证对应能力。

第二步，在搜索页输入问题。系统先准备检索计划，再向若干学术来源请求论文。你关注的不只是篇数，还包括实际调用了哪些来源、哪些失败、耗时在哪里。候选列表是线索，不是已经读完的研究结论。

第三步，选一篇论文。先看题名、摘要、年份和原文链接，再获取全文。自动找不到全文时，上传自己有权使用的 PDF。启动分析后，检查材料覆盖说明和实际读取图表页数，不要把“有 PDF 按钮”当成“模型已经看过全文”。

第四步，把有用分析整理成知识卡。比如“这篇文章使用的数据、方法、实验条件及局限”。保存前核对原文，特别是数据集、数值结果和方法名称。保存 AI 文本不等于自动确认它正确。

第五步，在智能体中建立研究方向文件夹和对话，选择材料来源，问“这些材料对计算成本有什么共同发现”。系统先找证据片段，再让模型回答。点回引用核对是否支持结论；材料不足时补材料，而不是不断要求模型说得更肯定。

第六步，从确认后的知识条目生成研究路线。把路线当成待讨论的研究计划：研究目标是什么，需要什么数据，怎样做实验，怎样判断有效。出图应当服务于解释这些关系，而不是用装饰掩盖内容缺失。

这六步的交接物依次是模型配置、论文候选、可读材料、知识卡、带来源回答和研究方案。只要某一步交接物不可靠，后面的语言再流畅也无法补救。

## 4 它是桌面软件 为什么又有网页

桌面软件不一定全部用传统桌面控件编写。ScholarNova 使用网页技术构建界面，再由 Electron 装进桌面窗口；启动时，Electron 还会启动本机后端。用户安装后直接打开应用，不需要自己启动开发服务器。

可以把整个应用想成一家小型资料室。React 是接待台，负责显示内容、接收点击；FastAPI 是后台办事窗口，负责安排搜索、分析和保存；SQLite 是账本；Electron 管理资料室的入口、窗口和启动过程。外部模型和学术来源，则是资料室需要联系的外部服务。

| 层次 | 当前技术 | 在项目里实际做什么 |
| --- | --- | --- |
| 桌面外壳 | Electron 和 electron-builder | 打开窗口、启动本地服务、制作安装包 |
| 操作界面 | React 和 TypeScript | 搜索页、知识库、对话、模型设置 |
| 本地服务 | Python 和 FastAPI | 接收请求，编排业务，调用外部服务 |
| 数据保存 | SQLite 和 SQLAlchemy | 保存论文、知识、路线和检索片段 |
| 文件处理 | PyMuPDF 和本地文件目录 | 解析 PDF，保存上传文件与生成图片 |
| 外部能力 | 学术 API 和模型 API | 获取论文线索，完成文字或图像任务 |

“前端”不是低级部分，“后端”也不是一定在远程服务器上。这里的前后端都可以在用户自己的电脑运行。界面使用本机地址，不等于你的资料全部在互联网上；但调用云模型时，本次请求需要的材料确实会被发送出去。

**代码入口**：desktop/main.cjs 中的 startBackend、startStaticServer 和 createWindow；frontend/src/App.tsx；backend/app/main.py。先读函数做了什么，不必从所有导入语句开始背。

**拓展学习**：读 Electron 的进程模型和 React 的快速入门即可起步，链接见第 20 章。先理解主进程管理窗口、界面进程负责显示，再学习跨进程通信。不要为了一个按钮直接放开界面的系统权限。

## 5 点一下搜索 按钮后发生什么

界面不会把搜索框内容直接交给任意模型自由执行。Search.tsx 先通过统一 API 客户端向本地后端提交请求。后端创建一个搜索任务，返回任务编号 run_id 和 HTTP 202，意思是“任务已接收，还在处理”。

随后前端定时询问这个任务进展如何。当前代码大约每 850 毫秒查询一次，并设置等待次数上限。这叫轮询。它像隔一会儿查看一次取件状态。另一种方式是 SSE，服务器在有进展时主动推送；当前研究路线生成使用 SSE，而不是所有页面都采用同一种机制。

真正的搜索工作在 backend/app/api/v1/search.py 的 _execute_search_task 中执行：准备查询、调用来源、合并结果、去重、筛选和排序。读代码时要从界面真实调用的入口追踪，不能仅凭某个文件名叫 orchestrator，就认定它一定在主流程里。

API 就是程序之间约定好的办事接口。请求里说明要办什么事，响应里给结果或状态。HTTP 是传递这些请求的一种通信方式，JSON 是常用的数据表达格式。比如一个任务响应可以包含状态、进度和论文列表；JSON 本身不会让内容变聪明。

FastAPI 是用 Python 编写这些接口的框架。它帮助接收请求、检查字段并组织返回值。它不会自动替你优化检索，更不会因为名字里有 Fast 就让外部模型立刻响应。实际速度还取决于流程设计、网络和第三方服务。

**最小阅读顺序**：Search.tsx → frontend/src/api/client.ts → search.py 的 create_search → _execute_search_task。每到一处只写三句话：收到什么，调用谁，返回什么。这样就能画出自己的调用链。

**小实验**：在开发环境观察一次搜索的网络请求，分清首次 POST 和后续 GET。可以用明确的精确查找示例，如 find the paper Attention Is All You Need。普通关键词仍可能触发查询规划模型并产生费用，不要默认它是零调用。不要把含授权头的网络记录发到公开仓库。

## 6 为什么多源搜索还会慢

学术来源不是一个巨大的共同数据库。Crossref、OpenAlex、Semantic Scholar 和 arXiv 的覆盖、字段、更新和访问限制不同。适配器的作用，是把不同来源返回的东西整理成应用能统一使用的论文记录。

并发检索像同时请几位同事查资料，而不是等一个人查完再叫下一个。它可以减少串行等待，但不能让某个来源的限流消失。某个来源失败时，应用应返回其他来源的有效结果，并明确缺失情况。

查询规划的作用，是把研究意图转换成可执行的搜索条件。AI 可能帮助生成更合适的英文词和子问题，但模型规划本身也要时间。当前实现先有规则方案，精确查找可直接使用规则；探索型问题才尝试模型规划，规划有时间预算，失败就使用规则方案。

因此，AI 辅助检索的目标应该是更快找到有用结果，而不是承诺每次按钮到结果的秒数都更少。如果简单题名搜索还先调用一次大模型，反而可能变慢。是否用 AI，要按任务选择。

限流中的 HTTP 429 通常表示请求过密或触及额度限制。“之前成功过”只证明当时那次请求允许通过，不代表现在无限调用。超时、401 认证问题、403 权限限制和 429 限流也不是同一类错误。

实际治理包括控制并发、尊重服务端等待提示、有限次数重试、利用缓存及单源失败降级。不能无限重试，也不能通过不停更换身份绕开限制。用户界面应显示来源名称、状态与耗时，帮助判断是在等谁。

**代码位置**：services/search/query_planner.py、retriever.py、services/sources/、core/rate_limiter.py。先看检索源公共接口，再看一个具体来源，不要一开始同时读四家实现。

**练习**：记录十次真实任务的总耗时、首个有效结果时间和成功来源数。分别统计简单检索与复杂问题，比较改动前后。不要只挑最快的一次作为“优化效果”。

## 7 为什么还要去重和排序

一篇论文可能同时出现在多个来源。若只拼接列表，用户就会反复看到同一篇。DOI 可以理解为出版物常用的稳定标识；有 DOI 时先利用它合并，没有时再比较题名等信息。但 DOI 缺失、版本不同或题名相似，都会增加判断难度。

当前主要去重方法是 DOI 和题名词集合相似度。它不是让大模型逐篇判断是不是同一篇。确定性规则通常更便宜、更快，也更容易测试；但仍需防止把名字相近的两篇不同论文合并掉。

排序回答的是“先给用户看哪篇”。相关性、年份、引用量和开放获取情况并不是同一个指标。引用多说明受到关注，不一定更符合这次研究问题；新论文也不一定比旧论文更适合。界面要把这些含义分开。

MMR 可以先理解成“别让排在前面的全都长得一样”。它在相关性之外考虑候选之间的重复程度，帮助展示有一定多样性的结果。多样性也是取舍，不是越分散越好。

当前外部论文检索用的是规则词匹配、约束和多种属性参与排序，再做多样性选择。不要把它讲成整条搜索链都已经使用向量检索。真正的 BM25、Embedding 和 RRF 组合，主要用于后面本地材料的问答检索。

**代码位置**：services/search/deduplicator.py、ranker.py。**练习**：给去重测试加入同 DOI 不同大小写题名，以及相似题名但不同 DOI 的样本；先写你期待的结果，再运行测试。只有预期清楚，测试失败才有意义。

## 8 找到论文和读到全文不是一回事

检索 API 常提供题名、作者和摘要，未必提供全文。原文链接可能只是出版社页面；页面能打开，也不表示后端已拿到可解析的 PDF。PDF 按钮是一个入口，不是全文分析成功的证明。

当前分析优先读取用户上传的 PDF，没有上传时再尝试开放全文。获取失败时，可以基于摘要分析，但必须说清材料范围。学校订阅通常还涉及校园网、统一认证和授权，不能用“让 Agent 去看”代替合法访问流程。

解析是把 PDF 里的内容转换成程序能处理的数据。PyMuPDF 可以读取文字、页面和其他结构，但 PDF 不像规整的数据库。双栏排版、跨页表格、公式和扫描页，都可能让提取结果变差。OCR 是从图片识别文字的另一类技术；当前程序不能宣传成已经完整解决所有扫描件 OCR。

当前代码会提取正文、章节、表格和图注，并最多选择三个图表页面送给视觉任务模型。这个限制控制了传输量和成本，也意味着不能说模型看过每一张图。视觉模型失败后，仍可用正文、表格和图注文字分析，但要保留这个区别。

长论文还会面临上下文预算。解析得到全部文字，不等于一次请求会把所有文字完整发给模型。真正需要关注的是：实际发了哪些段落，哪些页，是否截断，是否还能回到原文定位。

**代码位置**：api/v1/analysis.py 的 _load_document_context、_visual_pages、analyze_paper；services/pdf/fetcher.py 和 parser.py。返回字段 document_coverage、visual_pages_read 和 model_completed 分别说明材料范围、图表页处理和模型完成情况。

**练习**：分别用一篇文本清晰的 PDF、一篇扫描 PDF 和一篇没有全文的检索记录测试。写下界面怎么提示差别。若三种情况都显示同样的“全文深度分析成功”，这才是需要优先修复的问题。

## 9 知识库不只是另一个收藏夹

收藏论文回答“以后到哪里再找它”，知识卡回答“我从这篇文章确认了什么”。有价值的知识卡应该包括结论、适用条件、局限和出处。研究者自己确认后的笔记，比未经核对地保存一大段模型输出更适合作为后续问答材料。

当前保存知识条目时，可以选择 AI 润色；润色失败应保留原文。条目落库后，程序同步建立可检索片段。用户看到的是一张知识卡，检索程序可能看到它拆出来的几个片段。

Chunk 就是片段。把长材料按接近句子或段落的边界切开，是为了在提问时只取相关部分。当前知识切块目标约为 1200 字符，并有约 160 字符重叠。注意是字符，不是 Token；模型计费和上下文容量常按 Token 衡量，两者不能直接当成相同单位。

为什么需要重叠？一句结论可能在上一段末尾，条件却在下一段开头。适度重叠有助于保留连接，但重叠过多又会带来重复证据和额外成本。切块不是越小越好，也不是越大越完整就越好。

Hash 可以理解为内容指纹。内容变了，指纹也通常会变；程序借此判断旧片段是否需要重建。版本号则记录采用了哪套处理方法。它们帮助你避免“知识卡改了，检索还在引用旧内容”的问题。

**代码位置**：models/knowledge.py；services/features/knowledge.py；services/features/paper.py。**练习**：在测试中用同一段笔记建两次特征，比较片段 ID；改动一句后再次生成，观察变化。不要直接修改日常数据库来练习。

## 10 RAG 是先找材料再作答

RAG 是 Retrieval Augmented Generation，即检索增强生成。先别记英文：它就像开卷考试。程序先从材料里找出与问题有关的片段，再把问题和这些片段交给模型，要求答案围绕它们组织。

知识库存着资料，不代表已经具备完整 RAG。还需要解析、切块、检索、选择证据、构造上下文和生成回答。ScholarNova 已经实现这条有边界的本地材料问答流程，但不是一个可以无限读所有资料、无限自主行动的系统。

BM25 是一种按词匹配的检索方法。它考虑问题里的词在片段中出现的情况，也会区分过于常见与更有识别力的词。它不需要调用模型，成本低，适合精确术语，但对换一种说法的同义表达未必敏感。

Embedding 把文本转换成一串数字，用来比较语义接近程度。它不是压缩版的原文，也不能保证近的就是事实相关。项目只有在用户明确启用向量功能时才调用相应服务；向量模型与聊天模型是不同任务配置。

RRF 把不同检索方法各自的名次合并。可以想成几位评委的评分尺度不同，就先比较各自排在前面的候选，而不是把不可直接比较的分数硬相加。当前程序把 BM25 与向量检索结合，向量失败可以退回 BM25。

当前实现把向量保存在 SQLite 的缓存表，使用 Python 计算相似度，并没有独立部署 Milvus、Qdrant 或 Chroma。候选池和最终证据数量都有上限；最终最多六个证据片段，同一文档最多两个。这样控制成本和重复，也意味着材料规模增加后需要重新评估召回率。

**代码位置**：services/retrieval/bm25.py、hybrid.py、embeddings.py，以及 api/v1/agent.py。**练习**：对同一份材料分别问“推理延迟”和“响应要等多久”，观察词检索是否命中；再在你愿意承担调用费用时启用向量，对比收益。不要默认更复杂一定更好。

## 11 为什么有引用的答案仍可能不可靠

模型生成答案时会根据上下文组织语言。材料不足、指代不清、错误前提或检索到了不相关片段，都可能让它写出流畅但不被原文支持的结论。这类问题通常被称为幻觉，但排查时最好说出具体错误，而不是只说“AI 又幻觉了”。

例如，原文只在一个城市做实验，回答却说“已适用于全国”。即使句末写着正确的 [S1]，这句话仍然超出了证据。来源编号存在，只证明找得到来源；不能证明该来源支持这一结论。

当前回答校验主要检查来源编号及引用覆盖，失败后最多尝试一次修订，再失败则返回带来源的摘录。它没有完成对每句话的严格语义证明。因此，这套校验减少了一类错误，不是零幻觉保证。

“证据包”就是送给模型的精选材料及来源信息。它与“聊天历史”要分开：前者支持结论，后者帮助理解这次问题和代词。用户以前说过一句话，不应因为进入了聊天历史，就自动升级为论文证据。

当前科研问答没有找到证据时不会调用回答模型；产品使用帮助则有独立分支，可以用产品说明和近期对话调用模型。这正是解决“问你怎么用，却回答知识库没有材料”的关键区别。不同意图应该走不同流程。

控制长上下文，最有用的办法是先控制材料。保留相关原文、页码和章节，限制重复片段，给输出留预算；跨论文综合先分篇提取，再比较。摘要可以帮助理解，但关键结论仍应保留原文回查位置。

**练习**：准备三条问题：材料中明确有答案的、需要跨两篇比较的、材料完全没有涉及的。合格系统分别应给有依据的答案、有条件的比较和明确缺口，不是三条都回答得一样肯定。

## 12 换模型到底需要改什么

先分清四样东西。提供商是向你开放服务的平台；模型是平台提供的某个能力；API Key 是账号访问凭证；Base URL 是请求发到的地址。名字里都带 Qwen，不代表不同平台的地址、模型 ID、权限或价格完全相同。

“换 Key 不影响功能”的前提，是新配置支持这项任务。文字模型可以总结和规划，视觉模型可以读取图片，生图模型输出图片，Embedding 模型生成检索向量。一个 Key 有时能访问多类模型，但不能把这几种能力当成同一个模型接口。

项目用模型网关封装调用，用任务路由决定某种任务选哪个配置。这样界面不需要在每个按钮里写一次厂商专用逻辑。FastAPI 负责提供应用接口；真正帮助替换模型的是这层配置和适配，不是 FastAPI 自动实现的。

“OpenAI 兼容”通常表示某些请求或响应形式相近，不是所有功能一模一样。文本对话兼容，不代表图像生成、结构化输出、流式用量、思考模式和超时行为都相同。接入新平台必须按任务做小规模验证。

Temperature 影响采样时的随机程度，不是准确率开关。Max Tokens 是输出预算，不是写得越大越聪明。预算过大可能拖长响应或被平台拒绝；太小则可能截断答案。Timeout 是等待上限，也不代表服务器一定停止处理或不计费。

当前文本路由最多尝试一个用户明确启用、且不同的备用配置。视觉、出图和向量不全部共用这一机制。备用模型不是越多越可靠：多次尝试可能增加耗时、费用和材料外发范围。

**换模型验收**：先测短问答，再测结构化 JSON、中文总结和带来源回答；需要读图再测视觉，需要生图再单独测出图。记录真实模型名、响应时间和平台返回用量。不要只看“测试连接成功”。

**代码位置**：config.py 的 get_model_for_task、services/llm/gateway.py、services/inference/model_router.py，以及 api/v1/model_config.py。

## 13 智能体和 MCP 各自解决什么

智能体可以理解成“能围绕任务使用工具的程序”。关键不在于起了一个角色名，而是有明确目标、可用工具、执行边界和反馈。ScholarNova 当前更接近有界工作流：按规定步骤检索证据、生成回答、检查引用，必要时修订或回退。

这不是缺点。对个人科研工具来说，有界流程更容易控制成本和排查问题。现在并没有多个智能体自由讨论、反复调用工具直到自己认为成功的完整自主系统；不应该为了名字好听而这么宣传。

Zotero 联动当前通过本机 HTTP 接口完成。先确认软件启动并允许其他本机应用通信，再读取文库或集合。这里已经能实现联动，并不需要先引入 MCP。文件夹在 Zotero 中通常称为 collection；写入后回读目标，是为了避免导入到了错误集合却提示成功。

MCP 是把工具和材料以统一方式提供给 AI 应用的一种协议。普通 API 像一家工具自己的插座，MCP 更像统一接头。它能减少不同 AI 应用重复适配同一工具的工作，但不会自动赋予文献访问权限，也不会自动提高答案准确率。

将来如果要让不同助手读取 ScholarNova 的知识片段，或让 ScholarNova 接入多个已经提供 MCP 的工具，这时它更有价值。建议从只读工具开始，例如搜索知识、读取选定条目；涉及导出、覆盖、删除或收费调用的工具，要有更明确的用户确认和日志。

图书馆登录也不是“接个 MCP 就能完成”。合理流程应由用户在受控浏览器中完成学校认证，只处理有权访问的材料；不能把密码、整份 Cookie 或未经授权的全文直接交给模型。当前产品主要提供门户跳转和检索词传递，自动授权下载仍属于后续工作。

**练习**：给“查询知识条目”和“把论文导入文献管理器”分别写输入、输出、权限和失败提示。你会看到只读与写入的风险不同，这正是工具设计需要表达的内容。

## 14 数据在哪里 缓存为什么要分开

持久化是把数据保存下来，程序退出后仍在；缓存是为了临时加快读取，允许过期或丢失。两者目的不同。用户明确保存的知识不能按临时搜索缓存处理，离开页面后不再需要的结果也不应无期限堆积在界面中。

| 内容 | 当前主要位置 | 应怎样理解 |
| --- | --- | --- |
| 论文与搜索任务 | paper_entities 和 search_runs | 保存论文元信息和任务记录 |
| PDF 可检索内容 | paper_chunks | 保存片段及定位，不是原 PDF 本身 |
| 知识条目及片段 | knowledge_base 和 knowledge_chunks | 用户积累和检索所需数据 |
| 研究路线 | research_routes | 关联知识 ID 和生成分析 |
| 向量缓存 | retrieval_embeddings | 与提供商、模型和内容指纹关联 |
| 智能体对话工作区 | 前端 Zustand 持久存储 | 不是后端已有一张聊天记录表 |
| 原文件与生成图 | 用户运行时文件目录 | 与数据库一起构成完整资料 |

SQLite 可以看成一个本地数据库文件。SQLAlchemy 是让 Python 程序按对象方式操作数据的工具，也叫 ORM。表里的 ID 用来标识记录，外键或关联 ID 用来表达记录之间的关系。一个 PDF 可以有多个片段，一条研究路线可以关联多个知识条目。

当前搜索界面状态是临时的，后端结果列表也有内存缓存，默认有效期约一小时。当前缓存实现实际走内存，不能因为依赖列表里有 Redis，就宣称已经使用 Redis 服务。退出进程后内存会丢失。

数据库留下搜索任务和论文记录，也不等于旧搜索列表可以完整恢复：当前查询旧任务的接口主要从结果缓存取列表。以后若做历史搜索，应单独设计恢复逻辑和用户选择，而不是误把临时状态当永久档案。

桌面用户数据目录与源码目录不同。Windows 通常在用户 AppData 下的 scholarnova-desktop；备份应先退出应用，再复制完整数据目录。只备份一个数据库，可能遗漏上传文件、生成图片和设置。包含 Key 的备份也必须妥善保管。

**练习**：在测试数据库中画出“论文一对多片段、知识一对多片段”的关系，再试着新增和删除一条测试知识。观察对应片段是否同步变化。学习数据库先从这个小例子开始。

## 15 怎样让现有模型更可控地出图

先区分三种图。准确的架构图关心模块、连接和文字；基于实验数据的统计图关心数值、坐标和误差；展示插画关心构图、气氛和视觉统一。三者不应该都交给生图模型凭空画。

架构图适合让模型整理结构，再由 SVG 或绘图程序排版。SVG 是由文字描述形状和位置的矢量图，放大通常仍清晰，也更方便控制中文字体和标签。统计图应由真实数据驱动绘图程序。生图模型更适合示意插画、封面和视觉素材，不应用来生成“看起来像真实实验”的曲线或软件截图。

当前项目已经有两类路径：文字模型整理模块后调用生图接口；额外的结构提炼结果交给前端 SVG 引擎。现有生图请求主要沿用 SenseNova 的请求参数与返回结构。因此，把设置中的模型名换成 Qwen-Image，并不等于所有平台都已经适配完成。

文字版千问可以帮助编写设计说明，但只有具备图像生成能力的模型才能输出图片。硅基流动和百炼都有图像相关文档，具体可用模型、尺寸、图生图参数应按对应平台核对。质量取决于模型本身、任务类型、参考材料和迭代流程，不能承诺靠一段提示词就达到另一款工具的全部效果。

本轮已做的改进是先减少错误内容进入图片。过去提示词会默认鼓励补入注意力、奖励模块、公式或反馈箭头；现在不再把这些当作“专业感”的必需品。规划结果也要经过形状和长度校验，不合格时进入已有回退，不把异常字符串继续拼到图里。

新增校验限制模块数量、短标签和内部组件，保留有效技术术语；已有来源约束继续限制公式。新增 48 项测试与原有 14 项测试合计 62 项通过。这证明相关逻辑在这些样本上工作，不是一次生图效果评测，也不证明所有模块都忠实于原论文。

**仍需改进**：当前规则回退是建议骨架，不是原文复现；SVG 与生图尚未统一使用一份完全一致的结构；另一次结构提炼可能改变内容；连接边与来源映射尚需明确。要优先把这些问题解决，再追求更华丽的画面。

## 16 从一句要求到一张可靠图的具体做法

第一步写设计说明，不急着让模型画。说明图的用途、读者、必须出现的模块、模块关系、允许展示的文字、尺寸和参考风格。例如“用于论文方法部分，解释文献问答处理过程，只包含检索、证据选择、回答和引用校验，不画模型训练，不出现未测得的性能百分比”。

第二步把内容变成结构化数据。最重要的不只是模块名称，还包括每个模块来自哪段材料、连接方向表示什么、哪些内容是已有实现、哪些只是设想。JSON Schema 是对这种数据格式的约束，程序可以据此拒绝缺少字段或类型错误的结果；它只能检查格式，不能证明事实。

第三步先看简单预览。先确认模块没有漏、顺序合理、箭头不误导，再调整颜色和间距。正式论文图中文字优先由程序排版，英文缩写保留原样，中文标签保持短而准确。大量正文应放在图注或文中，不要塞进每个方框。

第四步按图的用途选择渲染器。架构图输出 SVG，统计图使用数据绘图；需要展示插画时，再把确认后的设计说明交给生图模型。参考图只借鉴布局和视觉，不照抄别人的实验数据、荣誉和品牌。

第五步检查结果。逐项核对标题、模块数量、名称、箭头方向和必要内容；再看文字是否清晰、是否遮挡、颜色是否一致。OCR 可以辅助发现拼写问题，但 OCR 没报错也不代表图的逻辑正确。

第六步保存版本和生成记录。保留内容结构、提示词、模型、参数、时间和原图。一次修改只改变一个方面，例如只调布局或只改标签。否则很难知道哪项修改真的改善了结果。

这些步骤是下一阶段的设计目标，不是已经全部加入界面的按钮。最小可交付版本应先做“用户确认结构后再生成”和“同一结构驱动 SVG 与生图”；之后再考虑受控次数的图像审查与重试，避免自动循环烧额度。

**可直接使用的设计说明示例**：这张图用于介绍科研问答流程。读者是第一次接触项目的研究生。内容为用户问题、材料检索、证据片段、模型回答、引用核验。只表达处理顺序，不画训练过程。中文短标签，白底，藏青主色、青绿强调，横向布局。每个阶段最多两条短说明。未知结果不填数字，产品截图使用真实截图。

## 17 怎样处理慢 失败和网络问题

慢首先是一个需要拆解的现象。点击到看到回答之间，可能包含本地排队、查询规划、外部检索、PDF 下载、解析、证据检索和模型输出。没有分阶段耗时，你很容易把下载慢误认为模型慢，或者把模型等待误认为界面没响应。

建议每次请求带一个追踪编号，记录阶段开始和结束、实际模型、来源状态、调用次数及用量。日志不要记录完整 Key、私人论文全文或认证 Cookie。追踪的目的是定位问题，不是尽可能收集用户资料。

降级是某项能力失败后，仍保留可用部分。例如一个检索源失败，继续给其他源的结果；向量服务失败，退回 BM25；视觉失败，说明只完成文本分析。降级必须显式展示，否则用户会以为完整能力已经成功。

重试也要有边界。认证失败通常不值得立刻重复十次；短暂网络错误可以有限重试。对写入操作还要考虑幂等：同一请求重复提交，不应反复导入同一条记录。生成请求超时后，服务端仍可能完成并计费，不能把没有响应当成免费。

代理会影响外部服务，也可能错误地接管本机通信。localhost、127.0.0.1 和 Zotero 本机接口一般应直连。学校馆藏则要按学校允许的网络方式访问。不存在“所有校园网和所有 VPN 永远冲突”的统一规则，要按实际路由和认证判断。

**排障顺序**：应用版本和启动状态 → 本机后端健康 → 模型地址与任务能力 → 账号权限与额度 → 外部网络 → 请求内容和输出预算。每次只改一个因素，保留失败类型，别一着急同时改 Key、地址和模型名。

## 18 测试 发布和安全也是产品功能

单元测试检查小函数，例如去重或标签校验；集成测试检查几个模块连接是否正确；端到端测试从用户操作一路走到底。Mock 是用可控制的假响应替代外部服务，能稳定复现超时和错误，但无法证明真实厂商 API 当天可用。

所以验证要分两层。大量离线测试用于防止代码回归；少量真实调用用于检查协议、能力、延迟和费用。不能把 Mock 返回了一张图片，写成“千问生图已实测成功”。同样，真实短问答成功，也不证明长文献分析已经成功。

Git 提交记录源代码变化，GitHub 保存和协作这些记录；Release 才是用户下载版本的发布位置。源码提交成功，不会自动更新用户电脑里已经安装的应用。需要重新打包、启动检查，并在发布说明里交代变化与限制。

当前核对的源码版本是 1.2.5。本次出图逻辑修改是后续源码改进，不等于已经生成新的 Windows 或 macOS 安装包。版本说明应把这件事写清楚，避免“仓库修了，为什么我桌面还是老样子”的误会。

Key 不应提交到仓库，也不要放进前端打包文件。当前本地配置不等于使用了系统钥匙串加密；备份和共享日志时仍要处理凭证。资料在本地保存，也不代表调用云模型时没有外发，需要按本次任务说明发送范围。

论文、期刊分区和软件依赖也各有使用条件。开源不等于所有数据可以随意转载；不收费也不会自动免除许可证义务。项目已有第三方许可与桌面发行说明，发布时应跟着同版本材料检查，而不是只看仓库顶部一个许可证名称。

**一轮实用验收**：全新安装 → 配置模型 → 重复搜索同一词 → 分析有全文和无全文的论文 → 保存及修改知识 → 产品帮助与科研问答分开测试 → 来源回查 → 生成路线 → 导出 → 退出重开确认数据。每一步记录结果与失败原因。

## 19 你怎样逐步学会自己维护

第一阶段只读懂流程，建议用三到五天。跑通第 3 章的例子，为每个按钮写输入、输出和失败情况；按第 5 章追一条 API 调用。完成标志是你可以不看宣传稿解释一次搜索发生了什么，而不是看完某门课的全部视频。

第二阶段补足 Python 和接口基础，建议一周左右。学习函数、字典、列表、异常和 async/await，再看 FastAPI 的请求体与响应模型。做一个独立练习接口：输入论文题名和年份，检查字段后返回整理结果。不要拿正式数据练删除操作。

第三阶段理解前端状态，建议一周。学习 React 组件、props、state 和事件处理，理解 TypeScript 类型如何帮助发现字段错误。再看搜索页状态与智能体持久化工作区为什么不同。练习在测试页面增加一个耗时显示，不触碰检索算法。

第四阶段理解数据和 RAG，建议一到两周。读 SQLAlchemy 的表与关系，做知识条目增删改查，再跑切块和 BM25 测试。手工准备十个问题及证据位置，比较“检索没找到”和“找到后回答错”两种失败。先有这个小评测集，再调整检索参数。

第五阶段练习模型接入与出图，建议一周。为文本、视觉、向量和生图分别写能力清单；阅读一份模型 API 文档，比较项目请求与官方示例。用第 16 章的设计说明评估图，不以“看着震撼”作为唯一标准。

第六阶段负责一次完整的小版本发布。自己描述问题，提出最小改动，先补失败样本，再修改、测试、写记录、提交和打包。不要同时改十个方向。真正掌握项目的标志，是知道为什么改、能解释测试，以及出错时知道怎么回到上一个可靠版本。

## 21 接入本地千问意味着什么

可以把云模型看成外面的专业服务，把本地模型看成装在自己电脑里的处理能力。模型权重是保存模型参数的文件；推理引擎负责把它加载起来、接收输入并计算输出。仅有权重文件，还不等于应用已经能调用它。

Qwen2.5 是一个系列，必须确认具体型号。3B、7B 等通常表示参数规模；Instruct 表示面向指令交互的版本；量化版本通过降低参数表示精度来减少资源占用，可能付出一定质量代价。普通 Qwen2.5 文字模型、Qwen2.5-VL 视觉模型与 Qwen-Image 生图模型不能混为一谈。

如果权重已经在 Ollama 中注册，ScholarNova 可以使用现有 Ollama 配置，通过本机地址和模型 ID 调用文字能力，通常不需要云端 Key。如果保存的是 GGUF 文件或 Hugging Face 权重文件夹，先要确认哪个推理引擎支持其格式，以及该引擎怎样提供服务，不能把文件夹路径直接填进模型名称就指望可用。

接入本地模型后，你确实不再局限于依赖第三方云模型服务。不过应用仍可能通过本机 HTTP API 交流，这是接口形式，不是外包与否的判断标准。你的项目可以准确表述为支持云端与本地模型的混合部署科研应用，但不能因此说成自主训练了千问。

本地推理、RAG 和微调是三件事。本地推理只改变模型在哪里运行；RAG 在回答前提供材料，不修改模型权重；微调使用训练数据改变部分或全部模型参数。LoRA 是常见的参数高效微调方法之一。现阶段不必为了“不是套 API”就先做微调，应先证明现有模型在哪些稳定任务上确实不足，并准备合法、高质量的训练与测试数据。

本地也不一定更快。模型首次加载要时间，长上下文会增加缓存占用，显存装不下时可能把部分计算放到内存和 CPU，速度明显变化。显存除了放权重，还要承担运行和上下文缓存。权重下载体积不能直接等同于运行时所需显存。

作为容量判断的例子，6GB 显存的机器应先评估较小量化模型和短上下文，而不是直接把大参数模型和最大上下文一起开启。实际选择要看已有权重、其他程序占用和测试结果。本轮只检查了本机硬件及常见服务位置，没有加载你的模型，尚不能给出真实速度或效果结论。

**接入顺序**：确认文件位置与完整模型名 → 确认推理引擎与权重格式 → 只监听本机地址启动服务 → 单条短文本测试 → 配置到 ScholarNova 的一项文字任务 → 用固定样本对比云模型 → 再决定是否扩大承担范围。不要第一次就用整篇长 PDF 压测。

**优先尝试的任务**：短摘要整理、标题翻译、给定材料的结构 JSON。完整跨论文问答和长文分析仍要单独评测。当前检索规划与问答存在较短等待预算，本地冷启动可能触发超时；后续应按实际测量调整本地配置，而不是把所有任务等待上限一并放大。

**隐私边界**：本地文字模型不表示整个应用完全离线。学术搜索仍可能联网，云端视觉或向量功能也会发送材料；启用云备用模型会改变外发范围。要实现某次分析不外发，应核对这次操作的所有模型任务与备用配置，而不是只看主模型是不是 Ollama。

学习入口：Qwen 官方模型说明 https://huggingface.co/Qwen/Qwen2.5-7B-Instruct/blob/main/README.md ；Ollama 模型清单 https://ollama.com/library/qwen2.5/tags ；本机对话接口说明 https://docs.ollama.com/api/chat 。这些资料解释模型和接口，不代表你的本地服务已经接通。

## 22 用流水线整理开发思路

你之前参考的 LLM Twin 架构通常写作 FTI，即 Feature、Training、Inference。不要把这三个词当成必须复制的基础设施清单。借鉴它最有用的地方，是把准备数据、优化系统和实际回答问题分开，让每一类工作有明确输入、输出和验证方法。

数据采集先回答“东西从哪里来”。对本项目就是论文 API、用户上传的 PDF、知识笔记和授权的文献管理器记录。ETL 是提取、转换和加载：拿到原始数据，整理成统一格式，再保存到合适位置。做了 ETL 并不意味着一定要有大型数据仓库。

Feature 流水线回答“怎样让材料可检索、可定位”。解析正文、切块、保留页码、计算内容指纹、建立词检索或向量特征，都属于这里。它应在资料新增或修改时更新，而不是每次用户提问都从头把所有 PDF 解析一遍。

Training 流水线原本涉及训练或微调模型。但 ScholarNova 当前更需要评测和优化流水线：保留固定问题、正确证据和预期行为，比较检索、提示词和模型配置的变化。没有自己的训练流程，也可以把数据与推理部分设计得清晰可靠，不必为了凑架构而训练。

Inference 流水线就是实际服务这次请求：理解问题、选择任务、检索材料、组织证据、调用模型、校验和返回。在线推理最需要关注等待时间、错误恢复和外部调用范围。数据准备做得越充分，这一步越有机会减少重复工作。

监控与发布把它们连接起来。你需要知道一次答案用了哪版材料、哪个模型和哪份提示词；改动后哪些固定样本变好了，哪些变坏了。只有能够解释结果变化，所谓“持续优化”才不是凭一次展示效果下结论。

当前系统适合保持模块化单体：模块在代码职责上分开，但仍随一个桌面应用运行。微服务是把部分能力拆成独立部署的服务，会带来通信、运维和版本一致性成本；个人桌面产品没有必要为了架构图复杂而提前拆开。

**练习**：选一个“修改知识条目后再问答”的操作，画三栏：数据与特征更新、离线测试、用户提问。把每个步骤放入对应栏，标出哪些应只在资料变化时运行，哪些每次问题都必须运行。再对照 docs/FTI_PIPELINE_ARCHITECTURE.zh-CN.md，区分已经接入主流程的实现和未来计划。
