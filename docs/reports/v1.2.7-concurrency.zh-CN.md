# 1.2.7 源码：多任务稳定性与并发治理

日期：2026-10-02。当前是源码验收，不是新安装包发布公告。本轮没有加载本地模型，没有改动 LLM-Twin，也没有改写已安装客户端的配置、论文或对话。

## 为什么先做这一轮

“并发”不是单纯把线程数调大。检索、PDF 解析、模型生成和数据库保存各有不同的瓶颈；无限排队会让用户等更久，供应商限流后不断重试还可能放大费用。因此这轮先保证任务数量有界、失败可解释、旧结果不串入新操作，再逐步提升有效吞吐。

对标覆盖 Dify、RAGFlow、AnythingLLM、Open WebUI、Khoj、PaperQA2、DocsGPT、Kotaemon、Vane、GPT Researcher、LiteLLM、Zotero 和 Elicit。依据与取舍见 [官方资料对标报告](../research/peer-landscape-2026-10-02.zh-CN.md)，没有复制它们的代码或声称拥有它们的实测性能。

## 已落地的改变

| 问题 | 现在的处理 | 用户能感知到什么 |
| --- | --- | --- |
| 后台搜索无限创建 | 先预留容量，再创建记录和后台任务；有界排队及执行期限 | 忙时给出提示，排队与检索阶段分开显示 |
| 分析、问答等重请求同时挤入 | 在读取请求体、打开业务数据库会话前控制入口 | 超额返回 429 和重试提示，不开始这次模型调用 |
| 搜索超时/应用关闭留下子请求 | 等待子任务退出；始终关闭数据源连接；关闭时补记未开始任务的终态 | 减少后台悬挂任务和永久等待状态 |
| PDF 同步处理占用事件循环 | 解析、页图和上传校验统一进入单个专用线程，忙时拒绝继续堆积 | 不在事件循环直接执行同步解析；避免多个 MuPDF 调用重叠，不承诺原生代码持有 GIL 时完全无卡顿 |
| Redis 配置没有真正使用 | 同事件循环共享初始化与连接池；故障后降级有容量上限的内存缓存 | 不反复重连，不靠无限内存保存临时结果 |
| 相同文本的向量缓存并发写冲突 | 独立短事务、冲突忽略、缓存锁等待有界 | 缓存不可写时仍可使用本次生成向量，业务会话不被破坏 |
| 数据库写锁跨越模型等待 | 论文与知识库特征准备完成后，由 API 提交短事务，再等待 Zotero 或模型 | 一个慢分析不再因这条写事务阻止其他保存 |
| 单次检索产生过多子任务 | 输入来源数量校验、相同来源和查询去重、每轮最多 12 个子检索 | 不能用一个搜索席位无限放大外部请求；超限明确标记为本地策略而非虚报 API 调用 |
| 模型 SDK 连接遗漏关闭 | 成功、失败和取消都回收任务持有的客户端 | 减少重复使用后的连接泄漏 |
| 旧回答、旧论文分析迟到 | 请求身份校验和取消信号；替换 PDF 使旧分析失效 | 清空对话后不“复活”，切换论文不串结果 |
| 替换 PDF 后被旧分析写回旧索引 | 同论文材料准备、文件发布和索引提交串行保护，失败先回滚；模型等待在保护区外 | 新文件不再配上旧材料的检索索引，其他论文不被这把锁串行化 |

每轮 12 条限制针对子查询任务，不包含每源重试与元数据补全请求，不能当作总 HTTP 请求上限。

## 默认容量与边界

| 配置 | 默认值 | 含义 |
| --- | --- | --- |
| `SEARCH_MAX_ACTIVE` | 3 | 同时执行的搜索任务 |
| `SEARCH_MAX_QUEUED` | 6 | 额外允许等待的搜索任务 |
| `SEARCH_QUEUE_TIMEOUT` | 30 秒 | 等待执行席位的预算 |
| `SEARCH_TIMEOUT` | 120 秒 | 取得席位后的执行期限，不含排队；取消清理可能额外耗时 |
| `AI_MAX_ACTIVE` | 4 | 受控的分析、问答、翻译、模型配置/测试、知识生成及推荐 HTTP 请求 |
| `AI_MAX_QUEUED` | 8 | 上述请求额外允许等待的数量 |
| `AI_QUEUE_TIMEOUT` | 2 秒 | 上述请求的排队期限，超过返回忙碌提示 |
| PDF 工作容量 | 1，零等待队列 | 所有应用内 MuPDF 操作在同一线程串行执行 |

可在开发环境变量中调整，示例见 `backend/.env.example`。桌面用户无需安装 Redis 或编辑这些参数。AI 入口预算与后台搜索预算相互独立，**不是所有模型子调用共享的供应商并发上限**；不能因此推算真实模型吞吐。Semantic Scholar 原有账号限流与 Retry-After 处理继续保留。

`GET /api/v1/health/live` 提供 `capacity.scope=process` 和活动、待执行、拒绝、排队超时计数，不包含查询正文或 Key。`queued` 包括已经预留但事件循环尚未调度的任务，刚提交的瞬间可能高于额外队列上限；总预留量仍受“活动上限＋额外队列”限制。

反向代理部署必须在 ASGI 服务器配置明确可信的代理地址。应用不直接信任客户端自行填写的 `X-Forwarded-For` 或 `X-Real-IP`，防止切换请求头绕过限流。不要为了获得真实 IP 将所有来源设成可信代理。

内存缓存的默认上限为 512 条、32 MiB 编码键值内容，含 TTL 和 LRU 淘汰；这不是进程总内存上限。Redis 故障会在当前运行期统一降级，不自动发起重连风暴。使用多进程时，各进程仍有独立任务预算和内存缓存。

同论文材料锁也是当前进程、当前服务事件循环内的保护，闲置后自动回收；它不是多进程文件锁。上传先提交旧索引失效，再发布新文件并提交新索引。若重建失败，会保留已保存的 PDF、明确提示索引未完成，不重新暴露旧索引。

## 离线压力基线

直接运行生产使用的入口控制中间件，后端处理函数模拟 100 毫秒异步等待。不调用用户 Key、不请求公共学术服务，也不加载 GPU 模型。[原始结果](capacity-benchmark-2026-10-02.json)

| 场景 | 请求数 | 完成 / 忙碌拒绝 | 实际重任务峰值 | 已接收请求 p95 | 健康查询 p95 |
| --- | --- | --- | --- | --- | --- |
| 不启用入口保护，瞬间突发 | 100 | 100 / 0 | 100 | 113.513 ms | 1.557 ms |
| 启用 4 活跃＋8 等待，瞬间突发 | 100 | 12 / 88 | 4 | 287.025 ms | 1.464 ms |
| 启用保护，每 30 ms 提交一次 | 100 | 100 / 0 | 4 | 111.096 ms | 1.381 ms |

三种场景各做了 25 次健康查询，结束后活动与预留计数归零。忙碌拒绝具有明确 429、错误码和 Retry-After；不自动轰炸重试。保护后的突发请求不是全部排队完成，这是有意限制资源消耗的结果。

该实验使用进程内 ASGI，不经过真实 TCP、模型、PDF、SQLite 或公网网络；100 ms 是模拟等待，不是实测模型响应时间。因此它证明容量和反馈机制有效，**不证明问答更快、支持 100 个真实并发用户或线上 p95**。

复现：在 backend 目录执行 `python scripts/benchmark_capacity.py --output ../docs/reports/capacity-benchmark-2026-10-02.json`。耗时随电脑负载变化，资源边界比单次毫秒数字更重要。

## 你可以按这个顺序试用

1. **重复检索**：搜索同一关键词两次，两次都应进入明确的任务状态；第一轮未结束时新一轮的页面不被旧结果覆盖。
2. **切篇分析**：分析 A，切到 B 再回到 A，本轮 A 的结果仍在；离开搜索页后重新进入，不恢复旧的临时分析。
3. **替换材料**：A 正在分析时上传新 PDF，旧分析的迟到结果不得覆盖新材料的结果。解析忙时按提示稍后重试；上传提示区分保存成功与索引失败，保存文件本身不代表模型已经读完全文。
4. **对话隔离**：发送问题后离开智能体页，再进入并清空该会话，随后进入另一对话。已清理的问题不能突然收到旧回答，研究文件夹和已保存知识不受影响；当前会话正在发送时，清空和删除按钮会暂时禁用。
5. **并行操作**：在合理数量的论文之间启动分析，同时查看知识库。任务过多时应显示忙碌原因，按钮能恢复，而不是永久转圈。
6. **失败恢复**：模拟断网或暂时无可用模型时，检查实际失败提示；网络恢复后主动重试。缺失供应商用量不能解释成“免费”。

不要拿公共供应商或自己的付费 Key 连续发送 100 个请求来复现压力基线；使用上述离线脚本。

## 还需要继续做的工作

- **前后端统一取消协议**：本轮前端 abort 防止界面写回，后端处理自己的超时和关闭。浏览器断开不保证 ASGI 任务或供应商立即停止，也不保证免计费；后续应加入显式任务取消接口和全链路验证。
- **端到端等待预算**：搜索、入口排队和模型调用已有各自的期限，但尚未形成覆盖所有前端请求的统一网络截止时间；断网恢复测试不能推导所有网络黑洞都会在固定秒数内恢复按钮。
- **供应商级预算**：目前入口有界，仍需将任务内部多个模型/重排/向量调用计入统一账号预算，记录排队、首结果、执行、总耗时。
- **批量与部分结果**：长任务可恢复、增量索引、批量导出幂等、搜索先呈现可用候选，需要单独的状态契约与测试。
- **检索质量**：在真实研究主题和授权论文上验证召回、引用支持度、全文覆盖与成本，不能只以接口成功率评价。
- **多人服务**：身份隔离、分布式配额、持久任务队列及服务端数据库需要单独设计和压测；本轮没有把桌面应用变成多租户 SaaS。
- **运行中原生 PDF**：取消等待不会杀死正在执行的 C 解析，槽位与临时文件等后台函数结束后才释放；原生调用卡死也可能拖住优雅退出。单线程方案不支持 PDF 并行提速；如需强制终止和故障隔离，需另行验证 Windows/macOS 冻结包中的进程型 Worker。
- **向量分批用量**：缓存故障不再丢失已完成整次生成用量；若多个向量批次中后续批次失败，前面批次用量的完整上报仍待补充。

本轮的落点是已有功能更稳、资源占用可控，并保留明确的下一步，而不是宣称所有性能与质量问题已经消失。
