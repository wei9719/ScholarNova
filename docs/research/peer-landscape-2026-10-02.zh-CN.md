# ScholarNova 同类项目对标与实用优化路线（2026-10-02）

## 1. 这轮研究要解决什么

ScholarNova 的目标仍是面向个人研究者的桌面应用：检索文献、阅读分析、整理知识、回到材料问答，并把确认后的内容交给用户熟悉的文献工具。当前优先级不是继续加载本地模型，也不是搬来一整套企业平台，而是让已有功能在多个任务同时发生时依然可靠。

这里的“高并发”分成三个层次：一个用户连续搜索、分析多篇论文和生成内容；一个检索任务同时调用多个数据源；未来多人服务端部署。前两层现在就值得解决，第三层需要额外的身份隔离、跨进程协调和服务端压测，不能用桌面单进程测试替代。

本报告核查了 13 个官方项目或产品，以及 Semantic Scholar 的官方接入说明。事实部分只依据官方仓库、产品文档和 API 文档；不采用 GitHub Issue 中的机器人回复，不引用未经复现的性能宣传，不复制第三方代码。各项目仍在更新，以下是检索当日观察，不是长期不变的功能承诺。

## 2. 13 个对标对象：事实、借鉴点与边界

### 2.1 Dify：借鉴工作流错误处理，不搬整个平台

**官方事实。** Dify 提供工作流、RAG、模型管理和可观测能力。节点错误可以终止流程、返回类型匹配的默认值，或进入失败分支；迭代可以停止、继续或去掉异常项。其许可证在 Apache 2.0 基础上附加条件。[官方仓库](https://github.com/langgenius/dify)、[错误处理文档](https://docs.dify.ai/zh/cloud/use-dify/build/predefined-error-handling-logic)

**适配建议。** 多源检索采用“单源失败，其他源继续”；模型分析采用“失败明确展示，不把默认提示伪装成成功答案”。每个步骤输出统一状态、耗时和可恢复动作。

**成本与边界。** 它是应用开发平台，不是轻量论文桌面客户端。学习状态契约即可，不应为了几个节点引入完整部署栈；若复用源码，应单独审查所用版本许可证。

### 2.2 RAGFlow：文档解析质量应当可检查

**官方事实。** RAGFlow 支持模板化切分、片段可视化、可追溯引用及多路召回和重排。当前 README 对 Docker 部署建议的起点为 4 核、16 GB 内存、50 GB 可用空间，并说明实际需求随数据和并发变化。[官方仓库](https://github.com/infiniflow/ragflow)

**适配建议。** 先展示“取得哪些页、识别哪些图片、哪些内容未解析”，再生成分析。用户应能点到原页或证据片段，而不是只看到一篇流畅的总结。

**成本与边界。** 不能把它整包塞进普通电脑的安装程序。ScholarNova 可先保持轻量解析器，复杂 OCR 作为用户明确开启的高成本步骤；解析器与分析器分别限制并发。

### 2.3 AnythingLLM：桌面使用体验与模型配置分层

**官方事实。** AnythingLLM 提供本地和云模型、文档聊天、来源引用、工作空间及工具连接；README 明确部分多用户能力仅用于 Docker 版本。[官方仓库](https://github.com/Mintplex-Labs/anything-llm)

**适配建议。** 文件夹决定研究范围，会话决定临时上下文，模型配置决定任务执行方式，三者不要混在一起。更换回答模型时不应清空文献和会话；更换向量模型则要明确重建索引。

**成本与边界。** “应用运行在本机”不代表材料不会发送给云模型。设置页应分别说明回答、向量、重排、视觉请求发往哪里；不将其他产品的默认历史保存策略复制到我们的临时搜索页。

### 2.4 Open WebUI：状态、取消与迟到响应是一个整体

**官方事实。** Open WebUI 支持混合检索、来源事件及任务状态事件。其事件文档明确浏览器断开不自动取消后台任务，部分事件仍会写数据库；停止按钮另行调用任务停止接口。状态事件需要有终态，否则界面可能持续显示处理中。[官方仓库](https://github.com/open-webui/open-webui)、[事件与任务生命周期](https://docs.openwebui.com/features/extensibility/plugin/development/events/)

**适配建议。** ScholarNova 的搜索离页即清理，与该产品后台继续运行的策略不同。前端需要取消信号和请求代次校验，后端需要取消子任务及释放资源；新搜索不能被旧结果覆盖。

**成本与边界。** 多节点能力不等于开启多个进程就自动安全。若后续服务端化，进程内信号量、状态和缓存都需要重新检查。当前先将桌面单进程取消做完整。

### 2.5 Khoj：明确材料范围，比默认搜索全部资料更实用

**官方事实。** Khoj 支持个人文档与网络问答，可为智能体配置知识、模型和工具，提供语义检索和自托管方式；仓库标示 AGPL-3.0。[官方仓库](https://github.com/khoj-ai/khoj)

**适配建议。** 智能体进入某研究文件夹后，默认只用这个范围；跨文件夹比较由用户显式选择。产品帮助、一般解释、材料问答分路，避免“你会做什么”也去检索论文。

**成本与边界。** 定时任务、网络搜索和工具写操作需要额外授权及费用预算，不应默认开启。学习交互逻辑不等于复制其代码或沿用其许可证。

### 2.6 PaperQA2：先筛证据，再写答案

**官方事实。** PaperQA2 将论文发现、证据收集、答案生成分开，区分召回片段数量与最终来源数量，支持带并发上限的证据摘要。图表增强生成的描述与原文分开保存。官方也说明内部研究使用的部分文献资源不能开放共享。[官方仓库与说明](https://github.com/Future-House/paper-qa)、[证据收集实现](https://github.com/Future-House/paper-qa/blob/main/src/paperqa/docs.py)

**适配建议。** 别把 50 篇论文全文直接塞进同一次请求。先检索候选片段，再按相关性、来源多样性和上下文预算组装证据包。模型生成的图片描述不能冒充论文原文。

**成本与边界。** 每片段摘要、重排、向量请求都会产生工作量；多步骤 Agent 不应无限追加检索轮次。官方研究成绩不能直接用作 ScholarNova 准确率。

### 2.7 DocsGPT：重活与即时问答分开

**官方事实。** DocsGPT 支持来源引用、连接器、模型选择和 MCP 接入。官方架构将 API 与处理摄取、向量化的 Worker 分开，使用 Redis、数据库及向量存储。[官方仓库](https://github.com/arc53/DocsGPT)

**适配建议。** PDF 解析、批量向量化是重活，搜索状态、取消操作和聊天界面是即时交互。重活不能卡住处理这些交互的事件循环。

**成本与边界。** 桌面阶段先采用有界工作池和清楚的任务状态，不必立刻加 Redis、独立 Worker 服务及更多数据库。只有部署形态和实测负载需要时再拆服务。

### 2.8 Kotaemon：把引用做成用户能检查的界面

**官方事实。** Kotaemon 支持全文与向量混合检索、重排、图表问答，以及带高亮的 PDF 引用预览和低相关性提示；扩展文档格式会增加依赖体积。[官方仓库](https://github.com/Cinnamon/kotaemon)

**适配建议。** 引用卡片至少包含标题、页码或位置、原文片段和点击入口。材料不相关时说明原因和补充方式，不用泛泛的长篇回答掩盖缺证据。

**成本与边界。** 召回分数是排序指标，不是事实正确概率；界面不能把相似度直接显示成“可信度 95%”。图表理解也不能只靠摘要推断。

### 2.9 Vane（原 Perplexica）：给用户可理解的速度选择

**官方事实。** 原 Perplexica 仓库现重定向为 Vane。官方提供 Speed、Balanced、Quality 检索模式，使用 SearXNG，并支持选择搜索来源和引用回答。[官方仓库](https://github.com/ItzCrazyKns/Vane)

**适配建议。** ScholarNova 可把检索分成“快速查找”和“深入研究”：前者尽快给候选论文，后者再规划、扩展与重排；显示额外步骤，而不是两种模式只换个名字。

**成本与边界。** 模式更深通常意味着更多请求及更长等待，这里是工程推断，不是该产品实测结论。学术检索仍要优先规范学术 API，网页搜索不是全文授权的替代品。

### 2.10 GPT Researcher：并行只放在相互独立的步骤

**官方事实。** GPT Researcher 采用规划、执行、汇总的分工：先形成研究问题，执行者收集材料，记录来源后汇总；支持网络、本地材料及 MCP 数据源。[官方仓库](https://github.com/assafelovic/gpt-researcher)

**适配建议。** 不同学术源、互不依赖的论文片段可限量并行；最终答案必须等待经过校验的证据包。应先决定哪些依赖必须串行，而不是看到 await 就改成同时执行。

**成本与边界。** 多 Agent 会放大搜索、解析和模型调用次数。先用确定性流程完成常见问题，把多轮自主研究作为有预算、可停止的可选模式。

### 2.11 LiteLLM：并发、速率、重试是不同约束

**官方事实。** LiteLLM 的路由文档分别描述并发上限、RPM/TPM、冷却和重试。当前文档中，部署并发满时直接返回 429，而不是无限排队；该上限按进程计算，不跨 Worker 或 Pod。文档也区分路由器重试与供应商 SDK 重试。[路由文档](https://docs.litellm.ai/docs/routing)、[请求生命周期](https://docs.litellm.ai/docs/proxy/architecture)

**适配建议。** ScholarNova 先统一整个请求的总时限、最大尝试次数和供应商资源预算；网关只在允许的错误上有限重试，避免“外层重试三次，SDK 里面又重试三次”。

**成本与边界。** 不建议仅为限流再叠一个常驻网关。可以先在现有网关实现最小必要控制；多个 API Key 不能被当作绕过供应商限制的手段。

### 2.12 Zotero：集成应尊重原软件的数据边界

**官方事实。** Zotero Connector 内置 HTTP 服务提供 ping、saveItems 等端点；Web API 文档支持增量获取、条件请求，并要求处理 Backoff 和 429。云 API 一般建议不超过 4 个并发请求，文档另说明本机 API 不采用相同限流。[Connector 文档](https://www.zotero.org/support/dev/client_coding/connector_http_server)、[API 基础与限流](https://www.zotero.org/support/dev/web_api/v3/basics)

**适配建议。** 检测连接、读取集合、选择目标、执行保存、核对结果，分成明确步骤。批量导出要显示逐条状态及重复项处理，不因超时就盲目重发写请求。

**成本与边界。** 不直接修改 Zotero 数据库，不让 Agent 任意删除或重分组。其他文献工具优先通过 RIS、BibTeX 等标准交换格式覆盖；具体接口能力仍按实际版本检测。

### 2.13 Elicit：把长任务当任务，而不是永远加载的按钮

**官方事实。** Elicit 的 API 区分快速搜索与长研究流程。后者以 202 接收并返回 sessionId，阶段可包括检索、筛选、抽取和报告；配额不足会暂停，失败响应仍可能有先前完成阶段的结果。API 访问及图表处理能力受套餐约束。[官方 API 文档](https://docs.elicit.com/)

**适配建议。** 批量分析或生成综述应有任务编号、当前阶段、已完成部分和恢复动作。实时搜索仍保持轻操作，避免所有按钮都变成沉重工作流。

**成本与边界。** 只借鉴状态设计，不把 Elicit 作为未获用户选择的付费依赖。高阶模式需要提前说明范围与预算，而不是完成后才解释为什么消耗很多 Token。

## 3. 学术源限流不能靠增加线程解决

Semantic Scholar 官方接入说明给出的初始 API Key 速率为每秒 1 个请求，未认证请求共享公共额度，并可能在繁忙时进一步被限制。这意味着“我曾经调用成功”与“持续并发不会被限流”不是一回事。[官方 API 说明](https://webflow.semanticscholar.org/product/api)

对 ScholarNova 的建议是：各源分别限速和记录冷却，不让一个 429 阻塞其他源；读请求有限重试并遵循 Retry-After；等待超过本次预算时保留其他来源结果并提示该源暂不可用。正常请求成功后恢复状态，但不因为瞬时成功就立刻把并发拉满。不要为了减少 429 换 Key 轮询、换 IP 或抓取受限页面。

## 4. 第一轮实现优先级

以下都是面向 ScholarNova 的工程建议，不表示已经实现。具体修改与验收应以对应提交和测试报告为准。现有项目文档已记载多源并发、限流、混合检索及超时能力，这轮重点是检查这些能力是否跨入口一致，而不是重新发明同名模块。

| 优先级 | 先解决的问题 | 最小实现方向 | 可验证的完成条件 |
| --- | --- | --- | --- |
| P0 | 多个搜索或分析同时启动，资源失控 | 应用级容量与供应商级上限；有界等待；超限明确拒绝 | 压测观察到的在途上限不超过配置；取消、超时和异常后计数归零 |
| P0 | 点击停止只是停止显示 | 从界面到服务端传播取消；清理子任务；终态不可被迟到响应改写 | 取消期间无新供应商调用；已在途调用尽力中止；旧结果不会进入新搜索 |
| P0 | 重试风暴与等待时间叠加 | 单次请求总 deadline；统一 attempt budget；区分 401、400、429、超时与 5xx | 鉴权和参数错误不自动重试；实际上游次数受总预算约束 |
| P0 | 提交重复问题、重复保存 | 前端防重复提交；写操作幂等或结果核对 | 同一次用户动作只新增一条记录；用户再次主动搜索仍可以执行 |
| P0 | 并发优化没有基线 | 本地可控模拟源、慢源、429、断线、取消测试 | 报告 p50/p95、首批结果、失败分类、在途峰值、排队耗时，而非只报通过数量 |
| P1 | 用户不知道等在哪里 | 统一排队、检索、解析、生成、完成、失败、取消的状态与计时 | 每次操作有且仅有一个终态；失败后按钮可恢复；不永久转圈 |
| P1 | 多篇全文导致昂贵和幻觉 | 证据包大小、来源数、页数、Token 和研究轮数预算 | 引用能回原文；未取得全文明确标识；模型描述与原文分开 |
| P1 | 背景任务抢走交互性能 | 把批量解析与实时交互分开限制容量 | 批量任务运行时，取消和状态查询仍可及时完成 |
| P1 | 切换研究方向发生串话 | 文件夹、会话和搜索代次分别标识；统一缓存作用域 | A 文件夹问题不会误用 B 文件夹材料；离开搜索页清理临时结果 |
| P1 | 换模型后功能悄悄降级 | 按文本、视觉、结构化输出、向量等能力验证任务配置 | 不支持的任务明确提示；没有“连接成功所以所有功能成功”的误导 |
| P2 | 用户开始真正批量使用 | 导入/导出任务、增量索引、恢复与容量管理 | 中断后仅恢复未完成部分；缓存有容量与期限；不重复计费同一可复用步骤 |
| P2 | 未来多人服务 | 用户权限、共享限流存储、独立队列及服务端数据库方案 | 跨进程上限成立、不同用户材料不可串读；另做部署形态压测 |

### 4.1 先明确四种时间，避免“显示很快，实际更慢”

1. **排队时间**：还没有占到处理名额，不应算作模型生成时间。
2. **首批结果时间**：用户第一次看到可用文献，而不是第一次看到动画。
3. **执行时间**：数据源、解析器或模型真正工作的时间。
4. **端到端时间**：从点击到获得明确终态，包括排队和重试。

任何性能宣传都要说明测试环境、并发数、资料数量、网络条件及模型配置。离线模拟压测证明的是资源管理和故障处理，不代表真实外部 API 在同一压力下也有一样的速度。

### 4.2 桌面版建议的执行边界

```text
用户操作（会话 ID、请求 ID、取消信号、总时限）
  ↓
任务入口：校验输入 → 检查容量 → 有界等待或明确拒绝
  ↓
独立资源池：学术检索 / PDF 解析 / 模型请求 / 图像生成
  ↓
供应商策略：速率、并发、冷却、有限重试、隐私范围
  ↓
逐步结果与真实用量 → 校验证据 → 单一终态
  ↓
仅用户确认保存的内容进入长期知识库
```

这是责任划分，不要求每一层建立一个新类、进程或微服务。先复用现有模块，用最少代码补上缺口。应用退出应终止本次拥有的临时任务，不去停止其他项目或用户正在运行的软件。

## 5. 压测应覆盖的具体场景

| 场景 | 为什么要测 | 必须检查的结果 |
| --- | --- | --- |
| 1、5、20、50 个模拟请求同时到达 | 测容量和排队边界，不向公网供应商打压力 | 上限有效，拒绝可解释，内存和任务数不随等待无限增长 |
| 一路 100 毫秒返回、一路很慢、一路 429 | 检查故障隔离 | 快源结果先到；慢源和限流不会抹掉已获得的候选 |
| 在排队、请求途中、返回前分别取消 | 发现信号量泄漏和竞态 | 没有重复 release、没有永远占槽、没有迟到写入 |
| 搜索 A 后马上搜索 B | 复现用户最容易遇到的串结果 | A 不覆盖 B，B 仍能运行，历史来源统计不混入 |
| 供应商连续 401、429、500、无响应 | 检查错误分类与尝试总数 | 非重试错误立即说明；可重试错误按预算结束 |
| 一篇大 PDF 与简单问答同时进行 | 检查是否堵塞事件循环 | 问答入口、状态和取消仍可用；解析受独立容量限制 |
| 保存请求超时但服务端已经完成 | 防止重复知识条目/文献 | 再操作前通过幂等标识或结果查询确认，不盲目重复写 |
| 会话清空后迟到回答到达 | 检查临时缓存边界 | 已清理内容不复活；保留用户明确保存的知识条目 |

初始并发值应保守，由真实耗时、内存与供应商配额共同决定。不要直接复制其他项目文档中的示例值，也不要把“50 个模拟客户端”写成“支持 50 人真实同时分析全文”。

## 6. 证据、成本与隐私需要一起优化

**证据。** 论文标题和摘要、取得的全文、图表视觉输入、用户笔记是四种材料，不应合并成一个“读过全文”的标签。回答至少记录 source_id、定位信息、材料类型和引用片段。无证据问题可提供明确标注的一般解释，但不能伪造论文依据。

**成本。** 记录供应商真正返回的用量；缺失用量就是未知，不是零。重试、向量、重排和图像也应分项记录。可复用计算按内容哈希及模型版本缓存，但临时搜索结果按当前会话清理；两种缓存的目的不同。

**隐私。** 研究资料是否发送外部服务应由任务配置决定。外部文献、网页和 MCP 返回内容是数据，不应改变系统权限或调用隐藏工具。日志保留状态和耗时，不保存 API Key、Cookie 或全文请求体。

**工具权限。** MCP 是工具发现和调用的接口方式，不是绕过权限、自动获得论文全文或保证答案正确的技术。现阶段 Zotero 读取和受控导出可以使用明确接口；馆藏登录应由用户在可信页面完成，Agent 只在授权范围内协助，不接管密码或突破资源访问限制。

## 7. 此轮明确不做的事

- 不继续加载或改动本地大模型，不修改 LLM-Twin。
- 不为了“高并发”无上限增加线程、协程、重试或 API 请求。
- 不把现有桌面应用重写成完整 Dify、RAGFlow 或云 SaaS。
- 不把对标项目的宣传性能、用户量、奖项或星数写成自身成果。
- 不新增默认付费依赖，不把用户材料自动发送给新的服务。
- 不声称引用存在就足以证明结论正确，也不承诺完全消除幻觉。

最值得先交付的不是更多菜单，而是一次搜索能快速看到可用结果，一次分析知道读了哪些材料，一次失败知道原因并能安全重试，一次取消真正停止后续工作。把这四件事做稳，再扩大批量任务和长期研究能力。
